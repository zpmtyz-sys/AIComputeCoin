## 1. 底层逻辑:为什么"交付的算力"可以被代币化(且合规)

不合规的做法是"凭空发个币 + 拉散户接盘"。我们走相反方向:**先有真实交付,再有币**。

```
真实算力交付  ──计量──►  标准化单位 CU  ──按公开曲线铸造──►  CC 代币  ──交易所──►  价格发现/流动性
(supplier 自有)        (compute oracle)      (ledger, 透明排放)        (exchange)
```

三个支柱:

1. **可计量**:把异构算力(不同 GPU / 不同模型 token)折算成统一单位 **CU(Compute Unit)**。没有统一计量就没有定价权。
2. **可验证**:Proof-of-Delivered-Compute(PoDC)—— 不是"证明你烧了电",而是"证明你**真的交付了**可用算力"。基准挑战 + 实际任务校验 + 信誉 + 质押惩罚。
3. **可信任分配**:排放曲线、创世分配、团队归属全部公开写死(`tokenomics.py`),链下账本双分录守恒,生产再上链。这让它"可被尽调",而不是又一个空气币。

> 关键区别:Bitcoin 的币背后是"共识 + 算力消耗";ComputeCoin 的币背后是"**已交付的、可被消费的真实 AI 算力**"。后者有内在使用价值锚。

## 2. CU:标准化算力单位

```
1 CU ≜ 1 TFLOPS · 1 小时 的 FP16 等效算力
```

两种入账来源,统一折算到 CU:

- **GPU-hours 来源**:`CU = TFLOPS_fp16 × hours × 修正系数`
  修正系数 = 显存带宽修正(`(bw/base_bw)^0.3`)× 互联修正(NVLink 1.15 / PCIe 1.0)× 可用性修正(SLA)。
- **Token 交付来源(经 sub2api 网关的真实请求)**:`CU = delivered_tokens × token_to_cu(model)`
  不同模型/精度有不同的 `token_to_cu` 折算系数(集中在 `tokenomics.py`,可调)。

实现见 `backend/app/modules/compute/service.py`。所有系数集中、可改、有单测。

## 3. 运行时架构(当前 MVP)

```
┌────────────────────────────────────────────────────────────┐
│ 浏览器: 静态仪表盘  +  Swagger(/docs)  +  机构 API          │
└───────────────┬────────────────────────────────────────────┘
                │ HTTP/JSON (JWT)
┌───────────────▼────────────────────────────────────────────┐
│            ComputeCoin App (FastAPI 模块化单体)             │
│                                                            │
│  identity ─ relay ─ compute ─ ledger ─ exchange ─ mm        │
│     │        │        │         │         │        │        │
│     └────────┴────────┴────┬────┴─────────┴────────┘        │
│                            │ service 层互调(唯一合法跨模块方式) │
└───────────────┬───────────┴────────────────────────────────┘
        ┌────────┴─────────┐                 ┌──────────────────┐
        ▼                  ▼                 ▼                  
   PostgreSQL           Redis          sub2api 网关(外部独立服务)
 (业务/账本/订单簿)   (会话/锁/热数据)   (HTTP 适配,计量算力交付)
```

- **为什么是模块化单体而不是一上来就微服务**:6000 个用户量级、快速迭代、要让 AI agent 并行开发又保持稳定 —— 单体 + 严格模块边界是性价比最高的形态。每个模块已经按"未来可拆成独立服务"来设计(service 层无状态、通过接口互调)。
- **sub2api 是外部独立服务**:我们通过 HTTP 适配器与它对接(它跑在 8080,我们跑在 8788),**不 fork 它的源码**,以隔离 LGPL,见 `compliance.md`。

## 4. 数据流:从"贡献算力"到"可交易的 CC"

```
1. 供给方注册(identity) → 勾选来源合法声明
2. relay: 登记一条算力能力(自有 sub2api 网关 / GPU 节点),source_attestation 必填
3. compute: 周期性发起 PoDC 验证(基准挑战 + 交叉校验) → verified=True
4. relay/compute: 记录交付计量(GPU-hours 或 delivered tokens) → 折算成 CU
5. ledger: 排放调度器按公开曲线,把当期排放量按“各供给方贡献 CU 占比”铸造 CC
6. 供给方在 exchange 卖出 CC / 消费方买入 CC 去消费算力
7. 所有手续费进国库账户(透明),做市模块用国库/自有库存提供流动性
```

## 5. 角色与激励(合规版)

| 角色 | 做什么 | 拿什么 |
|------|--------|--------|
| 供给方 Supplier | 贡献**自有**算力/中转能力,通过 PoDC | 按贡献 CU 占比获得排放的 CC |
| 消费方 Consumer | 花 CC 调用算力 | 真实算力服务 |
| 交易者 Trader | 在交易所买卖 CC | 价差(自负盈亏) |
| 做市/流动性 | 公开策略提供买卖盘 | 手续费返还 / 价差(策略透明) |
| 团队/创始人 | 建设平台 | **公开披露**的团队代币桶(带 vesting)+ 公司股权 + 平台手续费(进国库,治理决定分配) |

> 创始人的合理上行来自:① 公开披露并带锁定期的团队代币;② 公司股权(VC 融资正规稀释);③ 平台手续费经治理分配。**不来自**暗中砸盘散户。

| 维度 | MVP(本仓库) | 生产化目标 |
