# 合规设计 / Compliance Design

> 本文档说明本项目在**软件层面**为合规所做的结构化设计。它**不是法律意见**。
> 在向公众募资、上线交易、跨境运营前,**必须**聘请证券/加密资产律师就具体司法辖区出具意见。
> 代码里凡涉及法律判断处,只放"钩子 + TODO + 需法律意见"标注,不冒充法律结论。

---

## 1. 与 sub2api 的许可证隔离(LGPL-3.0)

sub2api 采用 **LGPL-3.0**。我们的处理:

- **不 fork、不修改 sub2api 源码**。ComputeCoin 作为**独立应用**,通过 sub2api 暴露的 **HTTP API** 与其交互(适配器模式,见 `backend/app/modules/relay/sub2api_client.py`)。
- LGPL 的传染性主要约束"修改 LGPL 库本身"与"静态链接"。我们既不修改也不链接其代码,只是**两个独立进程通过网络通信**,因此 ComputeCoin 自身代码可保持 **MIT**,并允许后续版本闭源(由你掌控收益)。
- 若将来确需修改 sub2api 源码:那部分修改必须以 LGPL 回馈,应放在**独立的 fork 仓库**,与本仓库的 MIT 代码物理隔离。

> 结论:**集成 ≠ 衍生**。保持进程隔离 + HTTP 通信,是"复用 sub2api 能力"又"保住闭源选项"的合规做法。

## 2. 上游服务条款(ToS)风险 —— 继承 sub2api 的免责

sub2api 自带声明:使用其能力**可能违反上游(Anthropic / OpenAI 等)的服务条款**。因此:

- 供给方在 `relay` 登记算力能力时,**强制**勾选 `source_attestation`:声明所贡献的算力/账号**为其本人合法拥有/有权使用**,且自负上游 ToS 风险。
- 平台**不**汇聚、转售他人凭证;`relay` 存储的是"贡献者自有能力的引用 + 交付计量",验证未通过前不计入排放。
- 在用户协议(backlog: legal/ToS 文档)中明确风险与责任划分。

## 3. 证券属性:把代币做成"可主张为功能型"的形态

是否构成证券由律师按各辖区(美国 Howey、欧盟 MiCA、新加坡 SFA、迪拜 VARA 等)判定。软件层我们做的是**降低被认定为证券的特征**:

- **使用价值锚**:CC 用于**消费真实算力**(utility),不是单纯的收益凭证。
- **不承诺收益**:UI/文案/接口**不**出现"保本/高回报/必然增值"等表述(代理也被禁止生成,见 `CLAUDE.md`)。
- **透明分配 + 锁定期**:团队/投资人桶公开且带 vesting/cliff,降低"中心化牟利"特征。
- **去中心化路线**:治理与链上结算在 backlog,逐步降低单点控制。
- **KYC/AML 钩子**:`identity` 预留 KYC 状态字段与校验钩子;`exchange`/出入金接口预留合规拦截点(`api/deps.py::require_kyc`)。MVP 不接第三方 KYC 供应商,但接口已就位。

> ⚠️ 即便如此,在某些辖区它仍可能被认定为证券或受加密资产监管。**先拿法律意见,再决定面向哪些用户开放、是否需要牌照。**

## 4. 反洗钱 / 风控(AML)钩子

- `exchange` 与提现接口预留:大额延迟、持仓/提现限额、异常交易标记(MVP 为接口与字段,规则引擎在 backlog)。
- 所有资金流动均有**账本分录**,天然可审计(满足审计追踪要求的基础)。

## 5. 投资人沟通的合规姿态

- 本仓库是**技术与架构实现**,其存在与内容**不构成**证券要约、投资邀约或收益承诺。
- 融资应通过**正规渠道**(SAFE/股权/合规代币销售)并配律师文件;投资人联系 **水镜先生 zpmtyz@gmail.com**。
- "先开源后闭源由一人掌控收益"本身合法(MIT 允许),但**面向散户募资 + 暗箱独占**不合法 —— 本项目已用"透明分配 + 正规融资 + 公司股权"替代后者。
