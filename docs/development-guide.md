## 一、设计哲学(为什么这样做)

### 1.1 核心命题

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   AI 时代, 算力 = 石油                                           │
│                                                                 │
│   石油有: 标准化计量(桶) → 期货交易所(CME) → 金融衍生品           │
│   算力缺: 标准化计量(?) → 交易所(?)        → 衍生品(?)           │
│                                                                 │
│   ComputeCoin 填的就是这个空白:                                    │
│   CU(标准桶) → CC 代币(可交易单位) → 现货交易所(MVP) → 衍生品     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 合规优先

```
 ❌ 错误做法                           ✅ 我们的做法
┌──────────────────────┐           ┌──────────────────────┐
│ 暗中增发              │           │ 硬顶写死在代码里       │
│ 创始人独占            │           │ 公开分配 + cliff/vest │
│ 散户接盘              │           │ VC 融资 + 功能型代币   │
│ 池化转卖凭证          │           │ 供给方自有 + 来源声明  │
│ 承诺收益              │           │ 不承诺, 只提供工具     │
└──────────────────────┘           └──────────────────────┘
```

```
          供给方                                  消费方/交易者
            │                                        │
            ▼                                        │
    ┌───────────────┐                                │
    │ 1. 注册       │  POST /api/auth/register       │
    │    (identity) │  角色: supplier                 │
    └───────┬───────┘                                │
            │                                        │
            ▼                                        │
    ┌───────────────────────┐                        │
    │ 2. 登记算力能力        │  POST /api/relay/sources
    │    (relay)            │  source_attestation 必填
    │    kind=sub2api/gpu   │  → verified=False
    └───────┬───────────────┘
            │
            ▼
    ┌───────────────────────┐
    │ 3. 验证(PoDC)         │  POST /api/compute/verify/{id}
    │    (compute)          │  MVP: 自动通过
    │    → verified=True    │  生产: benchmark 挑战
    └───────┬───────────────┘
            │
            ▼
    ┌───────────────────────────┐
    │ 4. 记录交付               │  POST /api/relay/sources/{id}/delivery
    │    (relay + compute)      │  tokens/gpu_hours → 折算 CU
    │    计量: CU 标准化         │
    └───────┬───────────────────┘
            │
            ▼
    ┌───────────────────────────────┐
    │ 5. 排放铸造(每日)             │  排放调度器(后台)
    │    (ledger)                   │  daily_emission / 2^period
    │    按 CU 占比分配 CC           │  双分录: mint_source → user
    │    不变量: ≤ MAX_SUPPLY       │
    └───────┬───────────────────────┘
            │
            ▼
    ┌──────────────────────────┐           ┌────────────────────┐
    │ 6. 卖出 CC               │           │ 买入 CC             │
    │    (exchange)            │  ◄─────►  │ (exchange)          │
    │    限价/市价, 价格-时间   │  撮合     │ 用 USDC/BTC 买入    │
    │    手续费→国库           │           │                    │◄─── 消费方
    └──────────────────────────┘           └────────────────────┘
```

**并行开发规则**:
- identity / relay / compute 可以并行改(不同模块, 不冲突)
- exchange 与 marketmaker 可以并行改(但 mm 调 exchange, 注意接口)
- `core/` + `models/` + `tokenomics.py` = 高风险共享区, 串行, 单独 PR

## 五、撮合引擎工作原理

```
                新订单进入 (Taker)
                     │
                     ▼
          ┌─────────────────────┐
          │  1. 余额/冻结校验    │  买: 有足够 quote?
          │                     │  卖: 有足够 base?
          └──────────┬──────────┘
                     │ 通过
                     ▼
          ┌─────────────────────┐
          │  2. 查找对手盘       │  价格优先 → 时间优先
          │     (Maker 方)      │  买方找最低卖盘
          │                     │  卖方找最高买盘
          └──────────┬──────────┘
                     │ 有匹配
                     ▼
          ┌─────────────────────┐
          │  3. 逐笔撮合        │  trade_qty = min(taker.rem, maker.rem)
          │     按 maker 价成交  │  trade_price = maker.price
          └──────────┬──────────┘
                     │
                     ▼
          ┌─────────────────────────────────────────┐
          │  4. 结算(通过 ledger)                    │
          │     base:  seller → buyer              │
          │     quote: buyer  → seller             │
          │     fee:   buyer/seller → treasury     │
          │     (全部走双分录, delta 之和 = 0)       │
          └──────────┬──────────────────────────────┘
                     │
                     ▼
          ┌─────────────────────┐
          │  5. 更新订单状态     │  filled / partial / open
          │     记录 Trade      │  市价单未填完 → cancelled
          └─────────────────────┘
```

## 十、关键设计决策记录(ADR)

| # | 决策 | 理由 | 替代方案 | 状态 |
|---|------|------|---------|------|
| 1 | Python + FastAPI 做 MVP | Agent 友好, 可读性高, 迭代快 | Go/Rust(更快但 agent 改起来慢) | 已采纳 |
| 2 | 模块化单体(非微服务) | 6000 用户量级, 一个容器即可, 降低复杂度 | 微服务(过早优化) | 已采纳 |
| 3 | sub2api HTTP 适配器(非 fork) | 隔离 LGPL, 保住 MIT 闭源权 | Fork sub2api(LGPL 传染) | 已采纳 |
| 4 | Decimal + DecimalText(非 float) | 金额精度, 防止浮点漂移 | float(更快但不精确) | 已采纳 |
| 5 | 双分录账本(非余额表) | 天然审计追踪, 守恒可校验 | 单余额表(无审计追踪) | 已采纳 |
| 6 | Docker Compose 单机部署 | MVP 阶段最简, 一键拉起 | K8s(过早优化) | 已采纳 |
| 7 | MIT 许可(非 AGPL) | 允许后续闭源, 创始人控制权 | AGPL(强制开源) | 已采纳 |
| 8 | 端口 8788 | 避开 8080(sub2api) | 3000/9000(也可以) | 已采纳 |

## 十一、快速参考卡片

### 常用命令

```bash
make up        # 启动
make down      # 停止
make logs      # 看日志
make test      # 跑测试
make lint      # 代码检查
make fmt       # 自动格式化
make secrets   # 生成密钥
make dev       # 本地开发(SQLite, 不需要 Docker)

### 重要文件路径

```
tokenomics.py         → 所有经济参数的唯一事实来源
core/config.py        → 所有运行时配置
.env / .env.example   → 环境变量
docker-compose.yml    → 部署拓扑
CLAUDE.md             → Agent 操作指南(最重要的文件)
docs/workflow.md      → 任务积压(认领任务看这里)
docs/compliance.md    → 合规红线(不能做什么)
```

### 测试矩阵

```
test_tokenomics.py  → 经济学不变量(供给上限/减半/创世)
test_compute.py     → CU 折算公式正确性
test_ledger.py      → 双分录守恒 + 排放分配
test_exchange.py    → 撮合公平性(价格/时间优先, 手续费)
test_relay.py       → 能力登记 + 交付计量
test_app_smoke.py   → 端到端: 注册→水龙头→交易
